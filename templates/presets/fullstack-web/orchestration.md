## Intervention Policy

### Critical (Pre-approval Required)
- **Architecture changes that affect multiple teams or system-wide patterns**: tech-lead reviews and approves before any implementation begins. All affected team leads must be briefed. An ADR must be written and committed before work starts.
- **Security vulnerabilities or changes to authentication and authorization logic**: tech-lead is notified immediately and the work is treated as a blocker. backend-team-lead assists with investigation. A security-focused code review is mandatory before merging.
- **Production deployment or infrastructure changes**: tech-lead must approve the deployment plan. CI/CD pipeline must pass all quality gates. A rollback plan must be documented before deployment proceeds.
- **Database schema migrations affecting existing production data**: backend-team-lead designs the migration and tech-lead reviews it. A backup and rollback procedure must be verified before execution. Migration is tested in staging first.

### Standard (Post-review)
- **New feature implementation spanning both frontend and backend**: product-manager provides the user story. frontend-team-lead and backend-team-lead negotiate the API contract. Each team lead delegates implementation to their respective developer. Integration is verified in a shared staging environment.
- **Significant refactoring of existing modules**: The relevant team lead scopes the refactoring, ensures test coverage exists before starting, and reviews all changes. tech-lead is notified if the refactoring crosses module boundaries.
- **Adding new external dependencies (npm packages)**: Team lead evaluates the package for security, maintenance status, and bundle impact. tech-lead is consulted for dependencies that affect the overall architecture. A brief justification is added to the PR description.
- **API contract changes that affect existing consumers**: backend-team-lead proposes the change and frontend-team-lead must agree before implementation. Breaking changes require API versioning. Both teams update their code in the same release cycle.

### Low Risk (Autonomous)
- Styling adjustments, color changes, or spacing fixes within existing components
- Updating inline code comments or JSDoc documentation
- Fixing typos in user-facing text strings
- Adding or improving logging statements (non-sensitive data only)
- Writing additional unit tests for existing code paths
- Updating README or developer documentation
- Renaming local variables or improving code readability within a single file
- Adding Storybook stories for existing components

## Workflows

### New Feature
End-to-end workflow for delivering a new feature from requirements to production, coordinating product, frontend, and backend teams.

```
1. [product-manager] Write user story with acceptance criteria, success metrics, and explicit out-of-scope items. Confirm feasibility with tech-lead. Slot into sprint backlog. → frontend-team-lead and backend-team-lead receive the specification
2. [backend-team-lead] Design database schema (if needed) and API contract. Share API contract with frontend-team-lead for review and agreement. Delegate endpoint implementation to api-developer once contract is agreed. → api-developer implements endpoints; frontend-team-lead begins component design
3. [frontend-team-lead] Design component hierarchy and state management approach. Review and agree on API contract from backend-team-lead. Delegate component implementation to ui-developer with detailed technical spec. → ui-developer implements components in parallel with api-developer
4. [tech-lead] Conduct cross-cutting review: verify security, performance, and architectural alignment. Approve the feature for integration testing. → integration testing in staging environment
5. [product-manager] Verify all acceptance criteria are met in staging. Confirm success metrics instrumentation is in place. Approve the feature for production release.
```

### Bug Fix
Structured workflow for investigating, fixing, and verifying bugs across the fullstack.

```
1. [tech-lead] Triage the bug report. Assign severity (Critical / High / Medium / Low). Route to the appropriate team lead based on the affected system layer. → assigned team lead investigates
2. [frontend-team-lead] If frontend bug: reproduce the issue, identify root cause in component/state/API integration, delegate fix to ui-developer or implement directly if architectural. Write a regression test. → fix is reviewed and merged
3. [backend-team-lead] If backend bug: reproduce with a failing test, identify root cause in service/query/validation layer, delegate fix to api-developer or implement directly if architectural. Ensure the failing test now passes. → fix is reviewed and merged
4. [tech-lead] Verify the fix in staging. For Critical or High severity bugs, conduct a post-mortem: document root cause, timeline, impact, and prevention measures in /docs/postmortems/.
```

### Code Review
Structured code review process ensuring quality, security, and architectural consistency before merging.

```
1. [ui-developer] Open pull request with: description of change, screenshots (for UI changes), link to user story, and self-review checklist completed. Assign frontend-team-lead as reviewer. → frontend-team-lead reviews
2. [frontend-team-lead] Review against the frontend code review checklist: correctness, accessibility, performance, test coverage, Storybook story. Approve, request changes, or escalate to tech-lead if architectural concerns are found. → tech-lead reviews if escalated; otherwise merges on approval
3. [api-developer] Open pull request with: description of endpoint changes, example request/response, test results (npm test output), and self-review checklist completed. Assign backend-team-lead as reviewer. → backend-team-lead reviews
4. [backend-team-lead] Review against the backend code review checklist: validation, security, error handling, query efficiency, test coverage. Approve, request changes, or escalate to tech-lead if architectural concerns arise. → tech-lead reviews if escalated; otherwise merges on approval
5. [tech-lead] Conduct architectural review for escalated PRs. Verify cross-cutting concerns (security, performance, breaking changes). Approve or return with documented required changes.
```

## Communication Protocol

### Inter-Agent Communication Protocol

### Overview
All agents in the fullstack-web team communicate through structured, documented formats. Ad-hoc verbal agreements are not acceptable — all decisions, delegations, and escalations must be written using the prescribed formats.

### Communication Hierarchy

```
tech-lead <-> product-manager (peer, strategic alignment)
     |
     +-- frontend-team-lead -> ui-developer (delegation chain)
     |
     +-- backend-team-lead -> api-developer (delegation chain)
```

### Reporting Lines

- **ui-developer** reports to **frontend-team-lead** only. Never escalate directly to tech-lead.
- **api-developer** reports to **backend-team-lead** only. Never escalate directly to tech-lead.
- **frontend-team-lead** and **backend-team-lead** report to **tech-lead**.
- **product-manager** collaborates with all team leads and is a peer of tech-lead.

### Message Types and Formats

#### 1. Task Delegation (Team Lead -> Developer)
Use the DELEGATION format defined in each team lead's system prompt. Must include:
- Clear task name and context
- Technical specification with types and file paths
- Acceptance criteria (testable)
- Estimated effort
- Dependencies and blockers to watch for

#### 2. Progress Update (Developer -> Team Lead)
Use the PROGRESS UPDATE format. Frequency: at least once per day for in-progress tasks. Must be sent immediately when a blocker is discovered.

#### 3. Status Report (Team Lead -> Tech Lead / Product Manager)
Use the STATUS REPORT format. Frequency: end of each sprint cycle, or on request. Contains: completed work, in-progress work, blockers, metrics.

#### 4. Escalation (Team Lead -> Tech Lead)
Use the ESCALATION TO TECH-LEAD format. Escalate when:
- A decision has architectural implications beyond the team's scope
- Two teams cannot reach agreement on a shared concern
- A security issue is discovered
- An infrastructure change is needed

#### 5. API Contract Negotiation (Frontend Team Lead <-> Backend Team Lead)
Use the API CONTRACT formats from each team lead's system prompt. Process:
1. Backend team lead proposes the contract in writing.
2. Frontend team lead reviews and responds with approval or change requests.
3. Both team leads must explicitly agree in writing before implementation begins.
4. Contract is committed to /docs/api/ as the source of truth.

#### 6. Blocker Report (Developer -> Team Lead)
Use the BLOCKER REPORT format. Sent immediately when a developer is blocked. Team lead must respond within 2 hours during working hours.

### Communication Principles

- **Written first**: All decisions and delegations are written down, never only verbal.
- **Single point of contact**: Each developer communicates upward only to their direct team lead.
- **Acknowledgment expected**: When a message requires action, the recipient acknowledges receipt and provides an ETA for response.
- **No assumption of agreement**: Silence is not agreement. Explicit approval is required before proceeding.
- **Conflict resolution**: If two team leads disagree, the dispute is escalated to tech-lead with both positions documented in writing.

### Cadence

- **Daily**: Developers send progress updates to their team lead.
- **Sprint boundary**: Team leads send status reports to tech-lead and product-manager.
- **On demand**: Escalations and blocker reports are sent immediately when the situation arises.
- **Pre-implementation**: API contract agreements must be completed before either team begins implementation.

- [ ] Lighthouse performance score is 85 or above in CI
- [ ] All form inputs have associated labels and validation feedback is accessible
- [ ] Focus management is correct for modals, drawers, and other dynamic overlays

### Backend Quality (backend-team-lead)
- [ ] All request inputs (params, query, body) are validated with Zod schemas
- [ ] Authentication and authorization are enforced at the middleware layer
- [ ] No raw SQL string interpolation — all queries are parameterized
- [ ] Error responses follow the project envelope format: { data: null, error: { code, message } }
- [ ] No sensitive data (passwords, tokens, full PII) in API responses or logs
- [ ] Service layer tests achieve at least 80% coverage of business logic branches
- [ ] Integration tests exist for happy path and at least two error cases per endpoint
- [ ] All tests pass with zero failures (npm test)
- [ ] No TypeScript errors in strict mode
- [ ] P95 response time is under 200ms for read endpoints and 500ms for write endpoints in load testing
- [ ] New database queries use appropriate indexes (EXPLAIN ANALYZE reviewed)
- [ ] OpenAPI documentation is updated for all new or modified endpoints

### Overall Quality (tech-lead)

- [ ] No new security vulnerabilities introduced (npm audit clean)
- [ ] API contracts between frontend and backend are agreed upon in writing and committed to /docs/api/
- [ ] Architectural decision records (ADRs) are written for any significant design choices
- [ ] No circular dependencies between modules (checked by dependency analysis tool)
- [ ] Environment variables are properly documented in .env.example
- [ ] All new features are covered by at least one end-to-end test scenario
- [ ] Deployment runbook is updated if deployment procedures have changed
- [ ] CHANGELOG.md is updated with user-facing changes
- [ ] No hardcoded environment-specific values (URLs, credentials, ports) in source code
